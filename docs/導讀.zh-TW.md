# 導讀：自己設計一顆 CPU（給沒學過計算機結構的人）

這份導讀假設你從來沒學過計算機結構。讀完之後，你應該能用自己的話向面試官說明：
這個專案做了什麼、為什麼這樣做、怎麼證明它是對的。

## 1. 這個專案在解決什麼問題

CPU（中央處理器）是電腦裡真正「做事」的晶片。平常我們寫 C 或 Python，
從來不用管 CPU 內部長什麼樣子；這個專案反過來，**從電路開始，自己設計 CPU**：

* **核心 A（單週期）**：最簡單的設計，每一條指令在一個時脈週期內做完。
* **核心 B（五級管線）**：像工廠生產線一樣，同時處理五條指令的不同步驟，
  另外加上快取（cache）和分支預測器，是真實處理器會用的做法。

兩顆 CPU 都用硬體描述語言 SystemVerilog 寫成，可以在電腦上模擬執行真正的 C 程式
（CoreMark、Dhrystone 這兩個常見的效能測試程式），也可以用 Yosys 合成到真實的
FPGA 晶片型號（XC7S50）上估算要用多少硬體。

這是模仿 MIT 6.1910（計算結構）課程期末專題的**學習用重做**，不是新發明。
重點是「頂尖學校的工程流程」：先寫規格（黃金模型）、多層測試、證明測試抓得到錯、
量測效能並分析原因、誠實寫出限制。

## 2. 七個關鍵觀念（每個附一個生活比喻）

### 觀念一：指令就是一張「工作單」

CPU 看不懂 C 語言。編譯器（這裡用 clang）把 C 程式翻譯成一條一條的**指令**，
每條指令是 32 個 0 和 1，意思像這樣：

* `add a0, a1, a2`：把 a1 和 a2 這兩個「暫存器」（CPU 裡的小抽屜）的數字相加，放進 a0。
* `lw a0, 8(sp)`：到記憶體地址 sp+8 拿一個數字，放進 a0。
* `beq a0, a1, 目標`：如果 a0 等於 a1，就跳到「目標」那條指令繼續做。

**比喻**：指令就像廚房的工作單，「把洋蔥切丁」「拿冰箱第三層的蛋」「如果湯滾了就關火」。
這個專案實作的指令集叫 **RISC-V RV32IM**：32 位元、整數運算（I）加上乘除法（M）。

### 觀念二：CPU 每個時脈週期在做什麼

CPU 裡有一個不停跳動的時脈（clock），每「滴答」一次叫一個**週期**。
單週期的核心 A 在每個週期做完一整條指令的五件事：

1. **取指令（fetch）**：用「程式計數器 PC」當地址，從記憶體拿出這條指令。
2. **解碼（decode）**：看懂這 32 個位元在說什麼，讀出需要的暫存器。
3. **執行（execute）**：做加減乘除、比大小、算跳躍地址。
4. **存取記憶體（memory）**：如果是 load/store，就去讀或寫記憶體。
5. **寫回（write back）**：把結果寫進目標暫存器，PC 換成下一條指令的地址。

**比喻**：一位廚師從頭到尾自己做完一道菜，做完才接下一張工作單。
簡單、不會出錯，但因為一個週期要包含最慢的那條路（例如除法要 32 步），
時脈只能調得很慢。

### 觀念三：管線就是工廠生產線，危障是生產線上的塞車

核心 B 把上面五件事拆成五個「站」（IF、ID、EX、MEM、WB），每站之間放一排暫存器隔開。
每個週期每一站都在處理**不同**的指令：第 1 條在寫回時，第 5 條才剛被取出來。

**比喻**：汽車工廠的生產線，車體、引擎、輪胎、烤漆、檢查五個站同時在做五台車。
每台車一樣要經過五站，但每個時間單位都有一台車完成，而且每站的工作很短，
所以生產線的節拍（時脈）可以快很多。

但是生產線會「塞車」，課本叫**危障（hazard）**：

* **資料危障**：第 2 條指令要用第 1 條的結果，可是第 1 條還在後面的站沒寫回。
  解法一是**轉送（forwarding）**：結果一算出來就從後面的站直接「遞」到執行站，
  不用等寫回。解法二是**停頓（stall）**：如果是 load 要等記憶體，就讓後面的指令等一個週期
  （load-use stall）。
* **控制危障**：遇到「如果…就跳」的分支，要到執行站才知道跳不跳，可是後面已經取了兩條指令。
  猜錯就要把那兩條**沖掉（flush）**，損失兩個週期。
* **結構危障**：除法器一次只能做一個除法，要 34 個週期，這段時間後面的指令只能排隊。

想看它真的怎麼動：執行 `make pipeview`，打開 `build/pipeview.html`，
每一列是一條指令，每一欄是一個週期，看得到每條指令在每個週期走到哪一站、在哪裡停頓、哪些被沖掉。

### 觀念四：快取是放在手邊的小冰箱

真正的記憶體（DRAM）很慢，這個專案的記憶體模型預設要等 10 個週期才回應。
**快取（cache）** 是 CPU 旁邊很小但很快的記憶體，存放最近用過的資料，
而且一次搬 16 個位元組（一條 cache line），因為用了這個地址，附近的地址很可能等一下也會用到。

**比喻**：廚師身邊的小冰箱。要的東西在小冰箱裡（命中，hit）一伸手就拿到；
不在（未命中，miss）就要走去倉庫，順便把同一箱整箱搬回來。
小冰箱滿了就要挑一箱放回倉庫：這個專案的資料快取用「最久沒用的先放回去（LRU）」，
而且被改過的箱子要先寫回倉庫才能丟（write-back）。

核心 B 有兩個 4 KiB 快取：指令快取（I-cache）和資料快取（D-cache）。
量測結果：CoreMark 的資料快取命中率超過 99.99%；Dhrystone 因為程式碼放不進 4 KiB 的指令快取，
命中率只有 97.7%，換成 8 KiB 之後 CPI 從 1.40 降到 1.10。

### 觀念五：分支預測器是看經驗猜路

既然分支要到執行站才知道結果，那就**先猜**。分支預測器記得每個分支以前怎麼走：

* **BTB**：記住「這個地址是分支，上次跳到哪裡」。
* **2 位元計數器**：每個分支一個 0 到 3 的數字，跳了就加一、沒跳就減一，2 以上就猜「會跳」。
  連續兩次猜錯才改變主意，所以迴圈最後一次離開不會影響下一輪。
* **返回地址堆疊（RAS）**：函式呼叫時記下「回來的地址」，函式 return 時直接拿來用。

**比喻**：每天上學走同一條路，到路口不用停下來想，憑經驗直接轉彎；
偶爾遇到封路（猜錯）才倒回來重走。
量測結果：關掉預測器，CoreMark 要多花 20% 的週期。

### 觀念六：黃金模型和「逐指令對答案」

怎麼證明自己設計的 CPU 是對的？這個專案用 C 另外寫了一個**黃金模型**（`model/rv_iss.c`），
它只照規格一條一條執行指令，不管任何電路細節，因為簡單所以容易寫對
（而且官方的 riscv-tests 測試在它上面全部通過）。

兩顆 CPU 每做完一條指令，就從「commit port」報告：這條指令的地址、內容、寫了哪個暫存器、
寫了什麼值、寫了哪個記憶體位置。模擬程式同時讓黃金模型也做一條，兩邊**逐欄位比對**。
只要有一個位元不同，馬上停下來，印出出錯的那條指令和前面 8 條。這叫 **lockstep（鎖步）比對**。

**比喻**：考試時有一份標準答案，學生每寫完一題就馬上對一次答案，
錯了立刻知道是第幾題錯、錯成什麼，不用等整份考完才發現分數不對。

### 觀念七：證明測試真的抓得到錯（突變測試）

「全部測試都通過」可能只是因為測試太弱。所以這個專案故意把電路**改壞一行**
（例如拿掉轉送、拿掉 load-use 停頓、讓快取忘記標記被改過的資料），再跑一次測試，
確認每一種破壞都會讓某個測試失敗。16 個突變全部被抓到（`make mutants`）。

**比喻**：消防演習。偶爾故意製造一點煙，確認偵煙器真的會響。

## 5. 面試可能會問的 10 個問題

**1. 單週期和管線的差別？哪個比較快？**
單週期每條指令一個週期做完，CPI 剛好是 1；管線把工作切成五站，同時處理五條指令。
管線的 CPI 反而比較高（CoreMark 1.18），因為有停頓和猜錯；但每一站的電路很短，
時脈可以快很多。用 Yosys 估計的邏輯延遲是 56 ns 對 7.8 ns，所以整體大約快 6 倍。
不過這個估計沒有算繞線延遲，只能用來比較兩者，不是真的時脈。

**2. 什麼是轉送（forwarding）？什麼時候轉送也救不了？**
後一條指令需要前一條的結果時，直接從 MEM 或 WB 站把值送回執行站，不用等寫回暫存器。
救不了的情況是 load：資料要到 MEM 站結束才拿到，緊接著要用的指令只好停一個週期。
在 CoreMark 裡，這種 load-use 停頓佔了多出來的週期的 69%。

**3. 分支猜錯要付出多少代價？**
分支在 EX 站才確定，這時 IF 和 ID 已經各有一條猜錯的指令，要沖掉，所以是 2 個週期。
預測器在 CoreMark 上猜對 91.7% 的條件分支；關掉預測器，CoreMark 多花 20% 的週期。

**4. 你怎麼知道你的 CPU 是對的？**
三層：(1) 每個模組用 cocotb 對照 Python 寫的參考模型；(2) 官方 riscv-tests 50 個測試；
(3) 隨機產生的程式。後兩層都是 lockstep：每做完一條指令就和 C 寫的黃金模型比對。
最後用突變測試證明這些測試真的抓得到錯，16 個故意的錯誤全部被抓到。

**5. 黃金模型如果寫錯了怎麼辦？**
黃金模型自己要先通過官方 riscv-tests，而官方測試會自己檢查答案。
另外突變測試也故意改壞黃金模型的 MULHSU，確認會被抓到。
剩下的風險是「模型和電路犯了同一個誤解」，這一點在 DESIGN.md 寫明了。

**6. 快取為什麼要用 write-back，不用 write-through？**
write-through 每次寫入都要送到記憶體，記憶體要 10 個週期，等於每個 store 都要停或需要寫入緩衝區；
write-back 只在資料被擠出快取時才寫回，大部分 store 只寫快取。代價是 FENCE.I 時要先把髒資料寫回。

**7. 為什麼快取要「提早一個週期給地址」？**
FPGA 上的 block RAM 是同步讀取：這個週期給地址，下個週期才出資料。
所以管線在指令進入 MEM 站的前一個週期就把地址給快取，指令到了 MEM 站時資料剛好出來，
這個站只需要比對標籤。最麻煩的是停頓時要記得重給同一個地址。

**8. 什麼是 store bypass？為什麼需要？**
store 在時脈邊緣把資料寫進快取，而下一個存取在同一個邊緣讀同一個陣列，
block RAM 這時讀到的是舊資料。所以快取記住剛剛寫的位元組，下一個週期讀取時合併進去。
拿掉它，緊接在 store 後面讀同一條 cache line 的 load 會讀到舊值，測試立刻失敗。

**9. FENCE.I 是什麼？你怎麼實作？**
程式改寫自己的指令（例如 JIT）之後，要用 FENCE.I 告訴 CPU「指令改了」。
因為新指令是透過資料快取寫的，可能還沒到記憶體，指令快取也可能還留著舊的。
所以 FENCE.I 在 MEM 站等：先把資料快取的髒資料全部寫回，再清空指令快取，最後重新取下一條指令。
有趣的是官方的 fence_i 測試沒抓到「忘了清指令快取」這個錯，隨機測試抓到了。

**10. 這個專案最大的限制是什麼？下一步做什麼？**
只在模擬器上跑過，沒有放到真的 FPGA 板子，也沒有真正的時序分析（開源工具做不到這顆晶片的 timing sign-off）。
效能分數不是官方認證的。下一步：把乘法器切成兩級縮短關鍵路徑、
把 CPU 接到同系列專案 raycast-fpga 的影像管線上跑遊戲邏輯、
或者做亂序執行（out-of-order），現在的 commit port 和比對器可以直接沿用。

## 6. 加碼：浮點數和浮點運算器（FPU）

0.2.0 版替核心 B 加了一個「浮點運算器」（Floating-Point Unit，FPU），讓 CPU 能直接算有小數點的數。
這一節從「浮點數是什麼」講起。想邊看邊動手，先執行 `make fpdemo`（或雙擊 `跑跑看.command` 看最後一段）。

### 6.1 浮點數就是二進位的科學記號

很大或很小的數，我們會寫成科學記號：光速 3.0 × 10⁸、電子質量 9.1 × 10⁻³¹。
寫法固定是「正負號、一串有效數字、10 的幾次方」。電腦做一模一樣的事，只是底數換成 2：

```
數值 = (正負號) 1.xxxxx（二進位小數） × 2 的 e 次方
```

一個 64 位元的「雙精度」浮點數（C 語言的 `double`）把這三樣東西塞進 64 個位元：

| 欄位 | 位元數 | 意思 |
|---|---:|---|
| 符號（sign） | 1 | 0 是正，1 是負 |
| 指數（exponent） | 11 | 2 的幾次方（存的時候加上 1023，這樣不用另外存正負號） |
| 尾數（mantissa，也叫 fraction） | 52 | 小數點後面的 52 個二進位數字；前面那個「1.」不用存，因為一定是 1 |

32 位元的「單精度」（`float`）是 1 + 8 + 23。有效位數分別大約是十進位的 16 位和 7 位。

例子：`fpdemo` 印出 0.1 存在記憶體裡是 `0x3fb999999999999a`。拆開來看：
符號 0（正），指數欄位 `0x3fb` = 1019，減掉 1023 是 −4，尾數是 `999999999999a`。
所以它是 1.6000000000000000888… × 2⁻⁴ = 0.1000000000000000055…，不是剛好 0.1。

### 6.2 為什麼 0.1 + 0.2 不等於 0.3

十進位寫不出剛好的 1/3（0.3333… 寫不完），二進位則寫不出剛好的 1/10：
0.1 的二進位是 0.000110011001100…，無限循環。52 位元放不下，只能存「最接近的那一個」。
0.1、0.2、0.3 三個數存進去時各自都有一點點誤差，而且方向不一樣：

```
0.1       = 0.10000000000000000555   （比 0.1 大一點）
0.2       = 0.20000000000000001110   （比 0.2 大一點）
0.1 + 0.2 = 0.30000000000000004440   （兩個誤差加起來，再捨入一次）
0.3       = 0.29999999999999998889   （最接近 0.3 的數，其實比 0.3 小一點）
```

這四行是我們自己的 CPU 算出來印的。加出來的結果和「最接近 0.3 的數」差了最後一個位元，
所以 `0.1 + 0.2 == 0.3` 是假的。這不是 bug，是所有照 IEEE 754 標準做的電腦都一樣的結果；
我們的 FPU 也必須算出一模一樣的位元才算對。寫程式時的教訓：浮點數不要用 `==` 比較，要看差距夠不夠小。

### 6.3 捨入：放不下的位數怎麼處理

幾乎每次運算的真正答案都比 52 位元長，多出來的要捨去，這叫捨入（rounding）。IEEE 754 規定五種方式，
RISC-V 全部都要支援，程式可以用 `frm` 這個暫存器選：

| 模式 | 做法 | 生活比喻 |
|---|---|---|
| 最接近，剛好一半時取偶數（預設） | 四捨五入，但剛好卡在正中間時，選最後一位是偶數的那個 | 「銀行家捨入」：一半進、一半捨，長期加總不會偏高 |
| 往 0 | 直接把多的位數丟掉 | 無條件捨去 |
| 往下（往 −∞） | 永遠取比較小的 | 估算「至少有多少」 |
| 往上（往 +∞） | 永遠取比較大的 | 估算「最多有多少」 |
| 最接近，剛好一半時遠離 0 | 小學教的四捨五入 | |

`fpdemo` 的第二段用 1/3 示範：往下和往上算出來的最後一個位元不一樣（…5555 和 …5556），
負數的方向剛好相反。硬體裡，捨入只需要知道三件事：保留下來的最後一位、被丟掉的第一位（guard）、
以及再後面「有沒有任何不是 0 的東西」（sticky，黏住位元）。就像切蛋糕時不必量剩下的屑有多重，
只要知道「剛好一半、超過一半、還是不到一半」。

每次運算還會留下「旗標」，告訴程式剛才發生了什麼，總共五個：結果不精確（inexact，被捨入過）、
下溢（underflow）、上溢（overflow）、除以零（divide by zero）、無效運算（invalid）。
它們會一直累積在 `fflags` 裡，直到程式去讀、去清。

### 6.4 特殊的值：無限大、NaN、兩種 0、次正規數

指數欄位的兩個極端值被保留下來，表示不是普通數字的東西：

* **無限大**（±∞）：1/0、或是算出來的數大到放不下（上溢）。之後還能繼續算，例如 ∞ + 1 = ∞。
* **NaN**（Not a Number，「不是一個數」）：沒有意義的運算，例如 0/0、∞ − ∞、√(−1)。
  NaN 會傳染：任何運算只要有 NaN 進去，出來就是 NaN，程式最後檢查一次就知道中途出過事。
* **+0 和 −0**：兩種 0，比較時相等，但 1/(+0) = +∞、1/(−0) = −∞。
* **次正規數**（subnormal）：比「最小的正常數」還小的數。這時前面那個「1.」變成「0.」，
  精確度一位一位減少，慢慢靠近 0，而不是突然變成 0。硬體要多花工夫處理它（我們的除法器會先把它「對齊」，
  多花幾個週期）。

`fpdemo` 第三段把這些都算了一次，並印出每個運算舉了哪些旗標。

還有一個 RISC-V 特有的小規定叫 **NaN-boxing**：浮點暫存器有 64 位元，放單精度數（32 位元）時，
上面 32 個位元要全部填 1。如果把一個沒有這樣包裝的暫存器當單精度數來讀，就當它是 NaN。
這樣可以防止程式把雙精度的一半誤當成單精度數來用而不自知。

### 6.5 為什麼加法、乘法很快，除法和開根號要很多個週期

加法和乘法可以「同時」做：乘法其實是很多個部分乘積加在一起，電路可以把它們排成一棵樹一起加。
除法不行。回想小學的直式除法：要先試商、乘回去、相減、看餘數，才能決定下一位商是多少。
每一位都要等前一位的餘數出來，沒辦法同時算。開根號的直式算法也是這樣。

所以我們的除法器每個時脈週期算 2 個位元（把同一個「試減」電路連做兩次），
雙精度需要 56 個位元（53 個有效位元，加上捨入要用的幾位），也就是 28 個週期，加上前後處理一共 32 個週期；
單精度 18 個週期。加、減、乘和「融合乘加」（a×b+c 只捨入一次）則是 5 個週期：

1. 拆開：把 64 個位元拆成符號、指數、尾數，順便看是不是特殊值。
2. 乘和對齊：算出四個部分乘積；同時把要加的數移到對的位置（指數不同的兩個數，要先對齊小數點才能加）。
3. 加：把所有東西加起來。
4. 正規化：如果兩個很接近的數相減，前面會變成一堆 0，要找到第一個 1，把它移回最前面。
5. 捨入：依照捨入模式決定最後一位要不要進位，並產生旗標。

為什麼不在一個週期做完？因為光是 53 × 53 位元的乘法就比現在整個時脈週期還長（10.0 ns 對 7.8 ns）。
硬塞在一個週期裡，整顆 CPU 的時脈都要放慢，連不算浮點的程式也跟著變慢。
所以浮點指令像整數除法一樣，停在 EX 站等 FPU 算完，管線其他部分先暫停。

### 6.6 FPU 怎麼接進管線

* 多了 32 個浮點暫存器（f0 到 f31），和整數暫存器（x0 到 x31）是兩組不同的抽屜。
  轉送和 load-use 停頓的規則和整數一樣，只是各管各的。
* 64 位元的浮點數要讀寫記憶體時（FLD/FSD），我們的資料路徑一次只能走 32 位元，所以拆成兩趟：
  先低的一半，再高的一半。如果這 8 個位元組剛好跨在兩條 cache line 上，兩趟各自可能命中或未命中，都沒關係。
* 旗標在指令離開 EX 站時累加。猜錯路徑上的指令根本到不了 EX 站，所以不會留下假的旗標。
* 參數 `FPU=0` 時，以上全部不存在，CPU 就是原來那顆 RV32IM。

### 6.7 怎麼知道它算得對

浮點運算的正確答案只有一個（標準規定到每一個位元和每一個旗標），所以可以很嚴格地考試：

1. **先寫黃金模型**（`model/rv_fp.c`），只用整數運算，一步一步照定義算。
2. **請裁判**：柏克萊大學的 TestFloat 會出題並附上標準答案。黃金模型考了 64,478,064 題，全對。
3. **硬體考同一份考卷**：RTL 的 FPU 在模擬器裡跑同樣的 64,478,064 題，全對；
   再和黃金模型比 200 萬次隨機運算（專挑無限大、NaN、次正規數這些容易錯的）。
4. **放進 CPU 再考**：官方的 rv32uf、rv32ud 測試，和 1,000 個含浮點指令的隨機程式，全部逐指令對答案。
5. **突變測試**：故意弄壞 21 個地方（例如把「剛好一半取偶數」改掉、把 sticky 位元丟掉），確認每一個都會被測試抓到。

模型和硬體用的是不同的算法（就像兩個人用不同方法解同一題），答案一樣才有說服力。
開發時真的抓到一個錯：硬體對「(−∞) × NaN + (−∞)」多舉了一個「無效運算」旗標，是隨機比對在前 20 萬次裡找到的。

### 6.8 量到的結果

* **快多少**：同一份雙精度運算程式，沒有 FPU 時要靠軟體函式一個位元一個位元地算（一次加法約 175 個週期），
  有 FPU 後同樣的量法約 7.5 個週期。五個測試合計 13,624,530 → 723,846 個週期，快 **18.8 倍**；
  讓編譯器使用融合乘加指令後是 23.8 倍。
* **花多少**：多用 6,742 個 LUT、1,549 個正反器、12 個 DSP（乘法器）。整顆核心從佔晶片 28.5% 變成 49.2%。
* **時脈**：最長路徑估計從 7.8 ns 變成 8.0 ns，最長的那條仍然是整數乘法器，不在 FPU 裡。
  （和前面一樣：這是不含繞線的估計，沒有上板驗證。）
* **代價**：浮點指令會讓管線停下來等，所以浮點密集的程式 CPI 接近 3。真正的高效能 FPU 是「管線化」的，
  可以同時有好幾個運算在裡面；那是下一步可以做的事。

### 6.9 再多 6 個面試可能會問的問題

**11. 為什麼 0.1 + 0.2 != 0.3？**
0.1、0.2、0.3 在二進位都是無限循環小數，只能存最接近的 53 位元近似值。兩個近似值相加再捨入一次，
得到 `0x3fd3333333333334`，而最接近 0.3 的數是 `0x3fd3333333333333`，差最後一個位元。這是標準行為，不是錯誤。

**12. IEEE 754 雙精度的 64 個位元怎麼分配？**
1 個符號、11 個指數（加 1023 的偏移）、52 個尾數（隱含開頭的 1）。指數全 0 表示 0 或次正規數，全 1 表示無限大或 NaN。

**13. guard、round、sticky 位元是做什麼的？**
捨入時只需要知道被丟掉的部分是「不到一半、剛好一半、超過一半」。guard 是被丟掉的第一位，
sticky 是後面所有位元的 OR。有了它們加上最後一位的奇偶，就能做出五種捨入模式，不必保留完整的多餘位數。

**14. 融合乘加（FMA）和先乘再加有什麼不同？為什麼硬體要做？**
a×b+c 用兩條指令會捨入兩次，FMA 只在最後捨入一次，所以比較準，也少一條指令。
硬體上乘積有 106 位元，加數要在一個 163 位元的視窗裡對齊，再做一次寬加法。
我們把加法和乘法也交給同一條資料路徑（加法是 a×1+b，乘法是 a×b+0），省下一套加法器。

**15. 為什麼你的 FPU 是多週期而不是單週期或管線化？**
單週期不行：53×53 的乘法就要 10 ns，比現有的 7.8 ns 時脈還長，會拖慢所有指令。
管線化（同時多個運算在 FPU 裡）吞吐量最高，但要替飛行中的結果另外做轉送和沖掉的邏輯。
多週期是中間的選擇：每一步都短於 7.8 ns，指令像除法一樣在 EX 等，控制邏輯直接沿用除法器那一套，
代價是連續的浮點運算每個都要等 5 個週期。

**16. 你怎麼驗證 FPU？只跑幾個例子夠嗎？**
不夠。浮點的錯常常只出現在特定的捨入邊界或特殊值上。我用三層：先用 Berkeley TestFloat 的 6,400 萬組測資
驗證純整數寫的黃金模型，再讓 RTL 跑同一批測資（結果和旗標都要相同），最後在 CPU 上跑官方測試和隨機程式，
每條指令和模型對答案。再用 21 個突變確認這些測試真的抓得到錯。
